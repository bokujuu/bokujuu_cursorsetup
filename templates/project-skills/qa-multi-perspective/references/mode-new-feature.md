# モード: new-feature（新機能）

## 目的

課題・仕様・実装を起点に、リリース前のテスト観点とケースの抜けを減らす。

## 入力（最低限）

- 課題 / ユーザーストーリー / 受け入れ条件のいずれか
- 変更対象のコードまたはモジュール一覧
- 既存仕様との関係（拡張か置換か）

## 観点の追加ルール

- P1〜P3: UI / API の操作経路を中心に
- P4: 画面に見えない副作用（DB・キュー・ファイル）を必ず 1 件以上
- P6: 変更の**隣接**機能（同画面・同 API グループ）を明示
- P7: 受け入れ条件と実装の差分を列挙形式で

## ケース化の正

| 優先 | 根拠の種類 |
|------|------------|
| 1 | 受け入れ条件・仕様書の節番号 |
| 2 | 課題チケット ID + 引用 |
| 3 | コード（ファイルパス + シンボル） |

根拠なしのケースは `draft` 扱いとし、確定リストに混ぜない。

## 出力例（観点のみ・抜粋）

```text
P3 [敵対的操作者]: 同一リクエストの二重送信で二重登録されないか
  根拠: AC-12 / src/.../SubmitHandler.*
P4 [データ整合監査]: 一覧の件数と DB の COUNT が一致するか
  根拠: 仕様 4.2 集計要件
```
