# Buffer とクエリフォールディング

再計算抑制やフォールディング制御は、**配置の見直しの後**に検討する。無差別に入れるとメモリ増・実行場所の変化で遅くなることがある。

`Table.Buffer` は**高速化保証でも、クエリ間キャッシュの保証でもない**。主にそのクエリ内で、テーブルを具体化して再利用評価を抑える浅いバッファとして扱う。下流の folding を妨げ、読み込みやメモリ負荷を増やすことがある。

## 目的と関数

| 目的 | 関数の例 | 注意の要点 |
|------|----------|------------|
| テーブルを具体化し、同一結果の再利用評価を抑える | `Table.Buffer` | キャッシュ保証ではない。下流 folding を妨げ得る。小さく絞った後に限定 |
| リストを具体化し、再利用評価を抑える | `List.Buffer` | リスト全体をメモリ化。大きいリストでは慎重に |
| バイナリをメモリ上に載せ、以降の読み取りを安定させる | `Binary.Buffer` | 対象バイナリ全体を載せるイメージ。大容量では特に慎重に |
| 下流へのクエリフォールディングを止めたい（具体化が主目的でない） | `Table.StopFolding` | 高速化保証ではない。実行場所・挙動が変わり得る |

folding 停止自体が目的なら、まず `Table.StopFolding` の要否を検討する。再利用評価の抑制が目的なら、削減後の狭い表に `Table.Buffer` を検討する。混同しない。

## いつ検討するか

- 高コストな読み込み・結合の直後に、同一中間結果を**同一クエリ内の**複数分岐で参照している。
- クエリ分割により、同じ中間ステップが何度も評価されやすくなっている。ただし Buffer は**クエリ間キャッシュを保証しない**。分割した別クエリ同士で評価が共有される前提にしない。
- 小さい参照表を繰り返しマージするとき（参照表側）。
- 依頼で最適化・再計算抑制・フォールディング停止が明示されている。

**先にやること**: 表示・分類・ラベル付けだけの処理を最終側へ移し、再評価範囲を狭める。ソース直後の全件 Buffer は原則避ける。

## 導入ルール

1. 行・列を絞った**後**の、必要最小の位置に置く。
2. 導入前後で結果比較する（スキーマ、行数、キー重複、null/error、代表出力）。性能目的なら時間または Diagnostics と folding 状態も見る。
3. 改善が確認できない、または悪化したら戻す。
4. コメントに目的を一言残す。

## 導入時の報告

- どのステップに何を入れたか
- 目的（同一クエリ内の再利用抑制 / フォールディング停止 / 参照表の安定化 など）
- 想定リスク（メモリ・folding・実行場所）
- 比較結果（または未検証）
