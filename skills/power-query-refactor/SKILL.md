# power-query-refactor — Power Query M の編集方針

既存の Power Query / M を**意味を保ったまま**読みやすく・配置よく整える判断基準。  
帳票セルの品質は `excel-deliverable-quality`。リポ固有の export/import/COM は各リポの AGENTS / repo-local skill へ委譲する。

出典の一般化元: [references/sources.md](references/sources.md)。

## 三つの柱

1. **編集の基本方針** — 意味を変えず、責務と配置を整える（本ファイル）。
2. **notes（コメント）** — 目的と理由が分かるコメント（[references/notes.md](references/notes.md)）。
3. **Buffer / フォールディング** — `Table.Buffer` 等は第一手にしない（[references/buffer-and-folding.md](references/buffer-and-folding.md)）。

## いつ使うか / 使わないか

使う:

- 既存 `.m` の可読化、ステップ名整理、責務分割の**設計**
- notes 追加、データ処理の上下配置見直し（意味が変わらない範囲）
- 最適化・再計算抑制・Buffer / StopFolding の**検討**（実行計画を変える変更は検証必須）

使わない:

- 新規クエリの仕様実装、意図的なビジネスロジック変更（依頼があれば別タスクとして明示）
- Excel 帳票のレイアウト・数式品質のみの依頼（→ `excel-deliverable-quality`）
- 特定リポの export → import → validate 手順や Import Plan
- 案件固有の突合・デバッグ

`.xlsx` / `.xlsm` を成果物として更新する作業では、M 編集に本スキルを使いつつ、ブック側の品質・検証は `excel-deliverable-quality` と各リポの workflow に従う。

## 二種類の変更を分ける

| 種別 | 例 | 必須 |
|------|----|------|
| **意味保持の整理** | コメント、自明なステップ名、可読のための空白・セクション分け（評価順・式の意味が同じ） | 変更意図の報告。可能なら静的確認 |
| **実行計画を変え得る変更** | フィルタ／型／結合／集計の順序移動、参照表マージ化、`Table.Buffer` / `Table.StopFolding`、クエリ分割 | **結果比較を必須**（下節）。未実施なら未検証と明示し、本番反映しない |

### 結果比較（実行計画変更時）

変更前後で次を比較する（環境が無い場合は未検証を明示して止める）:

- スキーマ（列名・型）
- 行数、キー重複の有無
- null / error の発生箇所と件数の傾向
- 代表行または主要集計の一致
- 性能目的なら、更新時間または Query Diagnostics、および folding 状態の変化

## 編集の基本方針（常に）

1. **意味を変えない** — 型変換、フィルタ条件、結合キー、集計ロジックは明示依頼がない限り変えない。
2. **`let ... in` を保つ** — 最終返却ステップの意味を変えない。
3. **意味単位で整理する** — 入力 → 整形 → 結合 → 集計 → 出力。
4. **公開名・参照を壊さない** — クエリ名、他クエリからの参照、関数名／引数、ロード設定を原則維持。変えるなら全参照と依存を確認し影響を明示する。
5. **既存コメントは尊重する** — 十分な箇所は重複して書き換えない。

### データ処理配置

コストの概算は `行数 × 列数 × 分岐数/再評価回数 × 外部 I/O`。クエリ間キャッシュが期待どおり共有される前提にしない。

| 原則 | やること |
|------|----------|
| 早く減らす | 行・列の削減、不要な外部読み込み回避は上流へ（ただし folding 可能な処理を不用意に妨げる配置は避ける） |
| 分岐前を重くしない | 分岐条件・適用判定に必要なものだけを分岐前へ |
| 集計前を限定する | 集計粒度・集計値に効く正規化・補正だけを集計前へ |
| 遅く飾る | 表示区分・ラベル・分析軸だけのマッピングは最終段へ |
| 結合は高コスト | マージ・展開・置換は行数・列数が絞られた後を優先 |

Power Query 固有:

- `File.Contents` / `Excel.Workbook` を含む共通上流に、後段専用の処理を足さない。
- `共通上流 → 複数分岐 → Table.Combine → レポート` では、Combine 後に寄せられる処理を分岐前に置かない。
- 例外は、上流のフィルタ・分岐判定・結合キー・集計単位にその結果が必要なときだけ。差異と性能影響を明示する。

### 条件付き置換 → 参照表マージ

大量行の行ごと条件置換は CPU 側評価になりやすい（特に非フォールディングソース）。参照表化は**意味が同値であることを確認できるときだけ**行う。

必須確認:

- 参照キーが置換用途で**一意**（重複キーで行増殖しない）
- 結合種別（通常は Left Outer 相当）と、未一致・null・複数一致時の扱いが元ロジックと同じ
- 変更前後の行数・キー数が説明できる

満たせない場合は Join へ変換しない。

手順の目安: 小さな参照表を用意 → `Table.NestedJoin` → 展開 → 適用列へ反映 → 補助列削除。  
参照表側に「適用する／しない」や置換先を持つ列がある場合は、その意味をコメントで残す。表が小さいときだけ参照表への `Table.Buffer` を検討する（[buffer-and-folding.md](references/buffer-and-folding.md)）。

表示・分類・ラベルだけの振替は最終レポート側へ寄せる。数行・単一列の固定置換、またはソース側へ押し込める単純条件は直書きでもよい。

### 分割（任意）

長いクエリや複数責務が混在するときは、ソース／基本処理／マージ／集計／最終のような責務分割を**検討**する。  
中間名の目安は `[基本名]_[処理名]`、関数は `fn_` 接頭。分割は実行計画・依存を変え得るため、結果比較と呼び出し側確認を必須とする。ブックへの反映手順は各リポへ委譲する。

## 完了の目安

- 変更が「意味保持」か「実行計画変更」かを区別して報告できる。
- notes が [references/notes.md](references/notes.md) に沿っている。
- Buffer / StopFolding を入れた場合、目的・リスク・比較結果（または未検証）を明示する。
- ロジックや公開名を変えた場合は理由と影響範囲を明示する。
