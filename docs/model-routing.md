# Astra を前提にした運用

更新: 2026/09/05 23:42

主利用モデルは GPT-6 Astra。Cursor・Codex 共通のスキル原本を使う。モデル選択は各製品の設定で行い、スキル本文で思考順序・推論量・委譲人数を固定しない。

## 通常の作業

依頼の達成条件と必要な検証を示し、エージェント自身の継続・ツール実行・コンテキスト管理を使う。確認済みの成果を使って次へ進む。新しい指示は、それまでの完了分を生かして反映する。

非同期実行が利用できる環境では、独立した仕事を進めながら返されたIDで結果を回収する。依存する操作は結果を待つ。失敗・完了・保留を区別し、変化のない状態を連続ポーリングしない。APIのasync設定を、未対応のCursorやCodexツールに付け足さない。

通常の長時間作業に外側ループを重ねない。セッションをまたぐ再実行を明示的に構築する場合だけ、残作業・検証結果・再開位置を保存し、回数/時間上限、停止条件、同一失敗への対処を決める。

旧 `templates/loop-orchestration/` は手動展開する互換資料。Grok 4.5 / `composer-2.5` の例は過去環境用で、現在の推奨モデルではない。`CURSOR_MODEL` や `-Model` の値は実際のCLIで利用可能なIDを確認して指定する。API名 `gpt-6-astra` がCursor CLIでも同じとは仮定しない。

## スキルの境界

一般的な自律性・推論フェーズは基本指示に委ねる。スキルには業務固有の条件、再現手順、検証資産を残す。ユーザーの明示指示をスキルの既定より優先する。検証済みの小変更にテストや確認工程を追加しない。

削除・軽量化の個別判断と検証範囲は [監査記録](astra-skill-audit.md)。既存のSol/Terra/Luna MCPは用途別の補助接続として残し、メインモデルの選択とは分ける。

根拠: [OpenAI Astraガイド](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6-astra)。モデルの能力と製品側で使えるツールは別々に確認する。
